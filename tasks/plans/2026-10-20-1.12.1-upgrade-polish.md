# Plan: 1.12.1 upgrade polish (client acceptance)

**Spec (binding):** the user asked to "fix the issues that we are actually seeing… we need them to function properly else our client will not accept." These are the issues from the v1.12.0 sanity run on 2026-10-19. Each fix must make the observed behavior correct and clear to a user. Ship as patch release 1.12.1.

Observed issues:
1. **Wrong summary after a version upgrade.** A plain upgrade 1.12.0 → 1.12.1 printed "Done! Already installed — 215 items unchanged." The version was stamped 1.12.1, and one file was kept with the user's edits while the template had also changed.
2. **No-op re-run dirties git.** A same-version re-install that changed nothing rewrote `.company-os/manifest`, because only the `# Generated:` timestamp changed. `git status` then shows a modified file.
3. **Untracked build file.** The first `bash tools/build/build.sh` in a fresh install creates `.claude/.generated-by-company-os`. It appears as untracked after the user has already committed per the installer's hint.
4. **Too many `.user` copies on a legacy upgrade.** `--force` from a real 1.11 install with 2 real user edits saved 105 `.user` copies, because the installer can't tell unedited old template files from edited ones.

## Global Constraints
1. Never lose a user's edit silently. A file may be overwritten without a `.user` copy only if its content provably equals a template copy that Company OS shipped.
2. Bash 3.2 compatible (macOS `/bin/bash`). Guard greps under `set -euo pipefail`. No `${v,,}`, associative arrays or `mapfile`.
3. Every fix has a test in `tests/` that fails on the current code (state how you checked). Verify with `/bin/bash tests/run.sh` (commit first, because test_install archives HEAD), `bash tools/build/build.sh --check --strict` and `node docs/diagrams/render.js --check`, all green.
4. After editing `os/` or `CLAUDE.md`, rebuild adapters and commit them together.
5. Conventional commits, subject ≤72 chars, body explains why, with trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never push, tag or open PRs.
6. Release: bump `.company-os/version` to `1.12.1`, and add `## [1.12.1] - 2026-10-20` to the CHANGELOG with Fixed entries in plain language. Update any doc or diagram text that states the old behavior.

## Task 1: Fix the four upgrade issues

- **F1 Summary.** The final summary reflects what happened: "Upgraded A → B: N updated, M added, K kept with your edits" whenever the version changes, even if no files were written. "Already installed — nothing changed" appears only when the version is the same and nothing was written. The "Kept your edits…" block stays.
- **F2 Manifest stability.** Don't rewrite `.company-os/manifest` when its content apart from the `# Generated:` line is unchanged. A no-op re-run leaves `git status` clean, and the test must assert exactly that.
- **F3 Generated list.** The installer writes `.claude/.generated-by-company-os`, with the same format and content `build-claude.sh` would produce, whenever it installs or updates the Claude adapter. A first build after install then changes nothing tracked. The test runs install, commits as the hint says, runs `build.sh`, and asserts `git status` is clean. The list must stay correct on upgrade too.
- **F4 Known template hashes.** Add `tools/build/known-hashes.sh`, which generates `.company-os/known-hashes.txt`: for every template-owned path the installer manages, the sha256 of every distinct content that path has had in the repo's git history. Include the old Claude-era layout (`.claude/skills`, `.claude/agents`, `.claude/hooks`, `tools/`, `.company-os/docs`, `CLAUDE.md` section if applicable, `setup.sh`) and the current layout. Keep the format compact and sorted.
  - The installer ships this file. On a legacy or untrusted-manifest upgrade with `--force`, a file whose current hash matches a known hash for that path is treated as an unedited old template copy: it is overwritten with no `.user` copy, and the backup still happens. Everything else keeps today's `.user` behavior.
  - The release check verifies the file is fresh. Add a mode such as `known-hashes.sh --check`, called from `build.sh --check`, a test, or CI. Explain in CONTRIBUTING how it is regenerated at release.
  - Measure and report the file size.
  - The test reproduces the sanity scenario: install the real 1.11 tree from `git archive 15f3eed` using its own `install.sh` with a fake curl on PATH (see `tests/test_install.sh` for the existing legacy setup and reuse it), make 2 real edits, then upgrade with `--force`. Expect exactly the edited files (plus CLAUDE.md if its section differs) as `.user` copies, not about 100.
